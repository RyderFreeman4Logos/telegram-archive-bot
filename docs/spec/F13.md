## Problem
Document audio needs reproducible input selection, explicit voice settings, and resumable artifact creation. Invoking a CLI and immediately uploading its output cannot establish completeness or reuse work safely.
## Scope
Implement the typed Rust producer adapter and a persisted spoken-text representation. Support single-speaker synthesis and explicitly requested multi-speaker configurations. At the audited baseline speaker configuration is TOML; retain the seed and resolved voice mapping. Local TTS is explicit, does not silently fall back to Edge, and cannot currently be combined with multi-speaker mode. Reject unsupported combinations before starting. Run the CLI with bounded resources in isolated job directories, preserving useful failure diagnostics without secrets. Produce raw artifacts and manifests; route successful outputs through F14.
## Dependencies
F02 (configuration), F03 (SQLite/CAS storage), and F07 (process supervision). Use the document-version contract from F04 when integrating document inputs. F14 is required for user-visible audio delivery; F15 owns Telegram sends. Provide derivation-key material for F18 rather than duplicating its shared cache. F12 is an independent sibling producer and must not be a prerequisite for speech synthesis.
## Acceptance criteria
- The original document version and exact spoken text can be identified from every result.
- Different language, speaker assignment, rate, pitch, input version, or output-affecting configuration cannot accidentally reuse an incompatible cached result.
- Failed and interrupted runs produce no completed artifact; cancellation terminates child processes.
- Concurrent inputs with identical display filenames cannot overwrite each other.
- Single- and multi-speaker fixture jobs retain ordered segments and correct timing metadata when subtitles are requested.
- A delivery retry performs no additional TTS request; no producer path bypasses F14.
