# 07 — Verification & Release Gates

## Verification strategy
Use a small set of meaningful invariant, adapter-contract, and crash-recovery tests. Avoid tests that merely mirror private implementation details. Offline fixtures should be synthetic or appropriately licensed and contain no personal archive data.
CI runs formatting, linting, compilation, unit/integration tests, schema migration checks, and a reproducible fake-provider end-to-end scenario. Media tests use real FFmpeg/ffprobe when the integration test environment advertises those capabilities.

## Audio/client acceptance matrix
Record exact client version, operating system, delivery method, container/codec, file duration, returned Telegram duration, seek result, and playback-speed control behavior.
Test a short narration, an ordinary audio track below 20 minutes, and one above 20 minutes on the operator's chosen Desktop and Android clients. The 20-minute boundary is motivated by one audited Desktop code baseline; do not claim all clients share that rule.
A successful Bot API response and a valid local file are necessary but do not by themselves prove a client exposes a particular UI control. If a client differs, document the supported profile and expose a usable narration mode.
An actual user-failing file, if available later, belongs in a private reproducer. The prior synthetic concatenation experiment demonstrates a possible mechanism, not a confirmed diagnosis of the user's incident.
## Provider tests
Use deterministic fake model/translation/TTS/source providers for CI. Add opt-in live smoke tests for configured services. Assert schemas, provenance, timeouts, cancellation, and retained partial states without requiring paid endpoints on every commit.
For hymt, include a structurally complete response with an intentionally missing passage to ensure the app does not equate transport success with semantic completeness. State what completeness checks can and cannot prove.
For yt-dlp, test metadata-only vs actual download, postprocessor failure, final path discovery, and process cancellation. For md2audio, cover single-speaker, multi-speaker where supported, resolved voice mapping, and local-provider constraints.
## Evidence files
Keep `docs/verification/release-checklist.md`, a machine-readable capability/version manifest, and focused logs/fixtures stripped of secrets. Record performed checks as performed, skipped checks as skipped, and blocked live checks with the exact missing prerequisite.
Core issue closure requires its acceptance criteria to pass. The first release additionally requires all G01–G12 gates and live audio/client evidence. A release candidate may be published with clearly marked pending live validation; do not call it production-validated.
## Release sequence
1. Complete the core issue dependency graph and run CI.
2. Install into a clean disposable environment from documented instructions.
3. Run synthetic end-to-end sources, text, PDF, translation, narration, download, Git export, restart, and restore.
4. Run authorized live provider and Telegram tests with supplied test credentials.
5. Record client playback observations and final default profiles.
6. Tag the release only after documenting the validation status, runtime dependencies, backup procedure, and known limitations.
