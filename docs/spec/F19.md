## Outcome
A new operator can install, inspect, update, stop, back up, and restore the bot from public documentation.
## Implementation scope
Provide a Linux user-systemd unit, config/env examples, install and upgrade instructions, explicit restart/shutdown behavior, managed writable state paths, and documented tool installation/version policy. Optional container support must not become a prerequisite.
Implement doctor/status output for executable versions/capabilities, database schema, storage integrity/readiness, enabled providers, disk budget, queue/projection lag, and effective non-secret configuration. Network probes are explicit. Add structured redacted logging with request/job/phase/artifact correlation.
Document privacy of archive destinations, model/TTS provider selection, hot-reload limits, retention/GC, finite retry budgets, dependency upgrades, consistent backups, and rollback. Source fetching and configured internal model endpoints have separate network policies.
## Acceptance criteria
- A clean environment can install and run the offline synthetic workflow using the README.
- Missing optional tools disable their feature with a useful diagnosis; missing required configuration fails early.
- The systemd unit restarts as documented and terminates descendant processes cleanly.
- Doctor does not silently send Telegram messages or expose secrets.
- Logs and example configs pass focused synthetic-secret checks.
- The documented restore and rollback procedure works in an isolated directory.
- Live activation is clearly distinguished from successful compilation and local tests.
## Shared definition of done
Implemented behavior satisfies the criteria above, focused checks record actual evidence, relevant public documentation is updated, and no production secrets or user archive data enter the public code repository. Resolve dependency Spec-IDs to issue links while retaining the stable IDs.
