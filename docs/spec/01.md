# 01 — Product Scope & Acceptance Contract

## Product outcome
A self-hosted Telegram bot turns submitted sources into a durable personal archive and listenable audio. A user can submit a link or text document, receive useful derived text and audio, inspect status, cancel work, retry a failed stage, and retrieve an already generated artifact without paying for the same transformation again.
The code is public and reusable. Deployment configuration and archived user content remain under the operator's control.
## Required input and output behavior
- **X/Twitter:** Resolve provider-native status identity across URL aliases. Capture reply ancestors, nested quotes and repost relations, and supported X Article content through configured providers. Keep stubs when a related source is unavailable. Render a readable view without duplicating canonical source bodies.
- **Web articles and ThreadReader:** Extract readable text, title, author and provenance using an adapter with a documented fallback. Preserve retrieval and extraction status independently.
- **PDFs:** Validate the downloaded PDF, retain the original artifact, and attempt text extraction. A usable original PDF remains deliverable if extraction fails; report a partial result instead of claiming translated or spoken text exists.
- **Video/audio URLs:** Use yt-dlp for supported providers, retain canonical provider identity and useful sanitized metadata, and produce validated audio through the shared finalizer.
- **Telegram text documents:** Accept bounded Markdown and UTF-8 text attachments, preserve their content, and generate narration. Use isolated job directories even when filenames match.
- **Derived text:** Produce Chinese summaries, translations, and descriptive display filenames by configurable language policy. Keep original source, translation, summary, and narration script as separate typed artifacts.
- **Audio:** Support configurable narration voice-message and ordinary audio-track modes. Publish only validated artifacts and store delivery receipts.
- **Archive:** Store each canonical source revision once and project stable text/metadata/manifests to a configurable Git archive.
## User commands and interactions
Specify and document commands with stable semantics; the exact spelling below is a recommended default.
- `/help`: supported inputs, enabled providers, and default output policy.
- `/status <job>`: current phase, completed artifacts, retryable failure, and delivery state.
- `/cancel <job>`: request cancellation and terminate active descendant processes; retain already committed source and valid artifacts.
- `/retry <job>`: retry the failed or explicitly chosen stage using existing successful artifacts.
- `/get <artifact>`: deliver a retained, authorized artifact without recomputing it.
- `/refresh <source>`: fetch a new observation and create a revision only when meaningful content changes.
- `/resend <delivery>`: deliberately retry an uncertain delivery after warning that an earlier send may have succeeded.
A normal repeated source submission reuses stored content and matching derivations according to the configured freshness policy. A forced transformation creates a new run without overwriting old outputs.
The ingress parser should accept URLs in text, captions, and Telegram entity fields; define the treatment of multiple URLs in one update. Persist separate child jobs with a common request ID and stable order. Unauthorized requests are rejected before downloading or invoking models.
## Core scenarios
### A, B, and C share a source
Archive A, then B quoting A, then C replying to A. There is one canonical record for A and one content revision when A has not changed. B and C have independent identities and relation edges to A. Each submitted view pins the exact revisions selected for that view.
A later refresh of A must not silently rewrite the earlier view. A quoted excerpt cannot replace a known complete A. Deletion or fetch failure records an observation and preserves previously archived content.
### Reliable listening
A 3-minute narration and a 25-minute download are both validated for actual duration, decoding, final size, and selected container profile. Telegram receives the measured duration and correct type. The returned media metadata is recorded. Short narration uses the configured voice-message mode and is checked on the target client for speed controls; ordinary audio-track controls may vary by client.
### Recoverable work
After an update is durably accepted, a process crash never leaves it acknowledged with no job. Model or TTS success survives later upload failure. After restart, the worker resumes missing work without recreating completed artifacts. A send with a lost response is explicitly uncertain, not confidently failed or successful.
### Portable archive
Repeated projection of the same dataset produces no diff. A clean restore reconstructs entities, content revisions, relationships, and view membership from exported semantic data. A full backup also restores binary artifacts and operational state from SQLite plus the blob store.
## Boundaries of the first release
Core F01–F20 cover ingestion, canonical storage, ADK/hymt processing, external media adapters, durable delivery, Git export, recovery, and deployment documentation.
Optional F21 adds keyword and semantic retrieval. Optional F22 imports legacy local archives. Neither is needed to demonstrate the two original fixes.
A distributed multi-user SaaS, unrestricted autonomous browsing, arbitrary shell tools for LLMs, a web dashboard, automatic publication of the user's archive, and automatic edits to the old bot are outside this release.
## Product decisions to record
The defaults in this spec permit implementation to proceed: Chinese derived text, narration as voice messages, a single-host deployment with local SQLite, bounded graph expansion, and a separate archive repository. Expose these as configuration where meaningful. Record the final repository name, license review result, supported client versions, enabled source providers, and resource limits in release documentation.
