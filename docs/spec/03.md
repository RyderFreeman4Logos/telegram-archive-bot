# 03 — Canonical Storage & Git Projection

## Decision and scope
Build this subsystem in the **new public Rust bot repository**. No legacy modification or migration is a prerequisite for F01–F20. Legacy import is optional F22. Tests use synthetic fixtures; never copy credentials, personal archives, or operational state from the legacy repository into the public project.
Use **SQLite plus immutable content-addressed files (CAS)** as the authoritative store. SQLite owns normalized text, identities, revisions, relationships, views, jobs, delivery state, and export state. CAS owns retained raw payloads and binary artifacts, referenced by digest from SQLite. Both are required for a full backup. Markdown/JSON exports are a portable content projection. Optional F21 search indexes, including LanceDB, must be rebuildable from authoritative records.
This choice follows the workload: small transactional writes, uniqueness constraints, relational integrity, and reliable work scheduling. It does not depend on claiming that Lance lacks transactions. The inspected LanceDB Rust API also explicitly describes its primary-key declaration as **unenforced**. Application invariants are more direct to express with SQLite constraints.
Run SQLite on a local filesystem, with WAL, `foreign_keys=ON` on every connection, a configured busy timeout, and a durability policy documented in configuration. Start with `synchronous=FULL`. SQLite permits concurrent readers and serializes writes. Use short transactions and bounded writer coordination; never hold a write transaction while awaiting HTTP, an LLM, a subprocess, or Git. A future multi-host deployment requires a separate database adapter; do not place this SQLite database on a network share.

Use `STRICT` tables where supported, explicit `NOT NULL`, foreign keys, and unique constraints. Enforce identity atomically with insert/upsert; a prior application-level existence check is insufficient. A failed fetch creates an observation and retryable/missing state, not a completed content revision. An embedded preview must not overwrite a complete capture.
### Identity and revision rules
For X, identify a post by its platform ID, not a URL hash. `x.com` and `twitter.com` aliases and different handles for the same post map to one source. Treat edit-history relationships only as established by provider evidence; do not merge separate post IDs merely because their text resembles one another.
For generic web pages, canonicalization is conservative and adapter-specific. Do not globally remove parameters such as `s` or `t`, which may identify different resources. Retain submitted URLs and redirect evidence. Provider-proven aliases can merge identity; a claimed HTML canonical URL alone must not silently merge unrelated content.
Content hashes exclude volatile counters and fetch timestamps. Observations can change without creating new content revisions. Record extraction versions as provenance; identical normalized content can reuse a revision while retaining distinct observations. Preserve an old revision when source text changes. A deleted or inaccessible source gets a status observation, without deleting previously captured content.
### Exact A/B/C behavior
When A is saved, create source A and revision A1. When B quotes A, store B1 and the edge B→A; reuse A1 if its content is unchanged. When C replies to A, add C1 and the C→A reply edge. There are three canonical sources and three unchanged content revisions, regardless of submission order or repeated requests.
Rendering is a separate operation. A self-contained document or audio for B may deliberately include A's context. Its immutable view records A1 and B1, so subsequent updates to A cannot silently change an existing artifact. A view may offer an explicit refresh that creates a new view. Do not claim the revision fetched today necessarily equals what B's author saw when writing B.
Use a request-wide visited-node set and fetch cache, plus maximum node, depth, byte, and time budgets. Repeated encounters create references instead of repeated expansion. Cycles and unavailable ancestors remain visible in the manifest. Context-sensitive summaries use the entire view manifest as input identity; per-source translations can reuse unchanged source revisions through F18.
## Publication, recovery, and concurrency
CAS publication uses a digest-addressed final path and a unique temporary file on the same filesystem. Record a publication intent/lease, write and hash the bytes, validate them, sync the file, publish without overwriting an existing object, and sync the containing directory. Only then commit the `ready` blob reference and related records. Concurrent publishers of the same digest converge on one immutable object.
A crash after publication but before catalog commit leaves an orphan; a crash before publication leaves a partial file. Recovery and garbage collection handle both. GC requires a grace period and must respect active publication leases, retained views, artifacts, and backup pins. It must not delete a newly published blob between publication and catalog commit. GC fences expired publication attempts before deletion; catalog publication rejects a stale lease generation. Missing or corrupt referenced blobs are explicit integrity failures, never silently accepted cache hits. Keep filesystem writes confined to managed storage roots.
F05 inserts the inbound update and requested work before acknowledging receipt by advancing the Telegram polling offset. F06 atomically claims jobs using leases and bounded retries. Source/revision changes and the outbox entries for dependent work belong in one SQLite transaction. Workers publish only artifacts that have completed their validation step. Repeated updates may reuse processing results while retaining separate authorized delivery requests.
## Git projection: F16
The **public code repository and private user-data repository are separate**. Export destinations are explicitly configured. Automatic push remains disabled until a destination is configured; setup must explain that archive exports may contain private source content. Runtime databases, credentials, temporary files, and provider authentication data never enter the code repository.
Export one canonical copy per revision, for example `sources/x/<id>/revisions/<digest>/body.md`, with adjacent metadata, relationship records, and immutable view manifests referencing revision paths. Use stable ordering, UTF-8, fixed newline rules, schema versions, and content digests. Do not include export-time timestamps that change on every run. Original observation timestamps are legitimate data. Binary retention is an explicit policy; a manifest containing blob hashes alone is not a backup of those blobs.
Read a consistent snapshot, write files atomically, and serialize exports with a single projection worker. Persist export work in the transactional outbox. Advance the local projection checkpoint only after a successful commit; record push progress separately. A crash after commit must allow recovery by inspecting the manifest/commit and producing no duplicate content change. An empty diff is a successful idempotent export.
On an ambiguous push timeout, query the configured remote ref before retrying or marking the upload complete. If the expected commit is reachable remotely, record success. Never force-push, reset unrelated work, or resolve conflicting user edits automatically. Git failure leaves the authoritative archive available and export work retryable. Preserve the distinction between “archived”, “committed locally”, and “pushed”.
## Backup and restore: F17
Provide a consistent full backup using SQLite's backup mechanism and an inventory of every referenced retained CAS object. Pin those objects while copying. Include schema version, blob sizes/digests, configuration schema, and a backup manifest. Credentials are restored separately. Verification must detect absent or corrupt files before declaring the backup usable.
Restore into an empty isolated destination first. Verify schema compatibility, database integrity, foreign keys, object digests, and manifest completeness. Rebuild optional search indexes. Reconcile or expire interrupted job leases; leave external side effects paused by default. Restoring a backup must never replay old Telegram deliveries or pushes merely because the restored process starts.
**Git-only restoration restores the exported semantic archive to the export checkpoint.** It cannot recover omitted blobs, pending jobs, recent unexported observations, or complete delivery state. The restore report must state that scope explicitly. Full disaster recovery requires SQLite plus the referenced CAS objects. No recovery command overwrites a live installation without an explicit destination/action.
## Issue acceptance and dependencies
### F03 — SQLite and CAS authoritative storage
Depends on F01–F02. Implement migrations, transactional repository APIs, publication intents, immutable CAS, integrity checks, and GC coordination. Acceptance: concurrent insertion preserves uniqueness; FK violations fail; failures injected before/after blob publication and before/after catalog commit recover without a `ready` reference to missing bytes; GC cannot race an active publisher; missing/corrupt blobs produce actionable errors. Network work never holds a database write transaction.
### F04 — Source identities, revisions, relationships, and views
Depends on F03. Acceptance: all submission orders of the A/B/C fixture converge to three sources, three unchanged revisions, and correct edges; repeated and concurrent submissions do not duplicate canonical content. A text edit creates a new revision while prior views remain unchanged. Metadata-only observations do not create content revisions. Test URL aliases, semantically meaningful query parameters, stubs upgraded to full content, cycles, unavailable ancestors, and deterministic traversal under all configured limits.
### F16 — Deterministic Git projection
Depends on F03–F04 and F06. Acceptance: identical snapshots export byte-identically; a repeated run yields no content diff; every view reference resolves to its pinned exported revision or an explicit omission. Test crash-after-write, crash-after-commit, push rejection, ambiguous push success, and concurrent export requests. Private data cannot be exported into the public code repository by default. Git outages do not invalidate successful archival.
### F17 — Backup, semantic export restore, and disaster recovery
Depends on F03–F04 and F16. Acceptance: restore a full backup into a new empty directory and compare all retained revisions, edges, views, and blob digests. Missing/corrupt blobs fail verification. Demonstrate Git-only recovery with its declared limitations. Restored jobs and delivery records remain paused until reconciled; no Telegram or Git side effects occur during verification. Document recovery commands and a repeatable disaster-recovery exercise.
