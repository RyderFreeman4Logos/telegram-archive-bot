# 08 — Evidence & Decision Log

## How to read this page
This page separates user requirements, observed implementation facts, and recommended decisions. Observations were collected around 2026-10-22. Recheck compatible released versions when implementation begins; these are reproducible audit baselines, not promises about the newest available version.
The actual user-failing audio file was not available. No definitive claim is made about that incident's exact cause.
## User-directed constraints
The project is a fresh public Rust bot repository. LLM work should use ADK-Rust, with hymt, yt-dlp, and md2audio integrated. It must improve audio usability and eliminate canonical duplicate storage of related sources while retaining a committable Git representation.
The user did not mandate LanceDB as the final authoritative database. SQLite plus immutable blobs and optional LanceDB indexing is the proposed design.

## Observed problems translated into new-product requirements
The legacy bot tied an archive directory to a normalized URL and rendered related source bodies into each result. The canonical-model requirement follows from the lack of a shared entity/revision store, not from a need for a more fashionable hash algorithm.
An offline check found known X status aliases could get different keys, while a globally stripped query parameter could collapse distinct web queries. The new identity policy must be provider-aware and conservative for general URLs.
The old send path did not validate returned media duration/type as a completion gate, and generated media was not subjected to a shared full-decoding finalizer. That motivates a single artifact validation contract across TTS and downloaded media.
A synthetic MP3 concatenation experiment produced inconsistent estimated and decoded durations. Remuxing improved timing but retained a decode error; re-encoding yielded clean decoding. This is mechanism evidence, not a reproduction of the user's file.
The existing media helpers have useful features and should be reused behind adapters. Rust application logic does not require reimplementing those tools.
## Decision records
### D01 — Authority and constraints
Proposed: use SQLite plus immutable blobs for the authoritative dataset. Business operations need uniqueness, relationships, revision history, and atomic inbox/job/outbox updates. A vector index alone does not supply the application's entire consistency model.
LanceDB has transaction and versioning capabilities; this specification does not claim otherwise. Its unenforced primary-key API is a specific reason not to assume SQL-style uniqueness automatically. Optional LanceDB indexes remain rebuildable.
### D02 — One-way Git projection
Proposed: database transactions create immutable export events. A serial projector commits deterministic text and manifests, and retries pushing separately. Explicit imports create new revisions; there are no uncontrolled dual writers.
### D03 — Orchestration boundary
Proposed: ADK performs typed LLM orchestration. The hymt adapter retains the library's translation client boundary unless a separately justified API change is made. Host Rust code controls downloading, persistence, subprocesses, Git, and Telegram delivery.
### D04 — Audio profiles
Proposed: narration uses a configurable voice-message profile with client validation; music-like/downloaded audio can use a regular audio-track profile. Duration/indexing repair and speed-control UI are separate concerns.
### D05 — Greenfield open source
Required: fresh repository history and a public application codebase. Proposed: MIT OR Apache-2.0 for new code after dependency review. Personal data, live credentials, and local operational files stay outside the code repository.
