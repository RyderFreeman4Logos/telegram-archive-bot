# 05 — Audio Finalization & Telegram Delivery

## Purpose and boundaries
This specification defines the audio subsystem of a new public Rust Telegram bot. Implement it in the new repository; it does not require modifying, deploying, or repairing the legacy bot. The code repository must contain synthetic fixtures and example configuration, never production credentials or a user's archive.
The subsystem accepts Markdown-to-speech output from `md2audio` and downloaded media from `yt-dlp`, produces validated immutable media artifacts, and delivers those artifacts through Telegram. LLM transformations belong to the separate `adk-rust` workflows. Downloading, media validation, encoding, and delivery are deterministic Rust-controlled jobs; they do not require an agent to decide each operation.
Audio correctness and client presentation are separate acceptance conditions. A successful upload does not prove correct duration, complete speech, seeking, or a particular playback-speed control. No actual failing user audio sample has been inspected. Historical code review and a synthetic concatenation experiment identify mechanisms to prevent, not a proven diagnosis of every reported failure.
## 1. Producer adapters
Implement a typed `Md2AudioAdapter` behind an interface that can later use a library or service. The MVP may invoke the existing CLI. Use explicit executable configuration, argument arrays, generated absolute filenames, and a private per-job working directory. Do not interpolate shell commands or give subprocesses the bot token. Record the invoked adapter version and effective non-secret settings. Apply configurable time, input-size, output-size, disk-use, and concurrency limits; cancellation must terminate the subprocess tree and record an interrupted job.
First create and persist the exact spoken-text representation of the selected document version. Its rendering policy must preserve substantive content by default and explicitly describe treatment of tables, code, links, and speaker labels. Translation, summary, and original-text audio are distinct derivations. A summary must not silently replace a request to read the full document.
Support single-speaker synthesis and explicitly requested multi-speaker synthesis. At the audited baseline speaker configuration is TOML; preserve the seed and resolved voice mapping. Explicit local TTS does not silently fall back to Edge, and local TTS cannot currently be combined with multi-speaker mode. Validate this combination before starting. Record language, voice assignments, rate, pitch, and any random seed or speaker-configuration digest. A reusable derivation key includes the document version, spoken-text hash, adapter/provider version, and all output-affecting settings. Cache lookup must distinguish synthesis results from finalized delivery profiles. Failed or incomplete synthesis must never satisfy a cache hit.
The producer returns an immutable raw artifact reference and a structured manifest. It must not upload directly. A zero exit code and an existing filename are insufficient evidence of valid audio. Segmented synthesis also returns an ordered segment manifest; subtitle offsets follow validated segment timing, not estimated text length. `yt-dlp` follows the same producer contract under F12.
## 2. Shared audio finalizer
Both producers enter one finalizer. Its steps are:
1. Wait for the producer to finish and close its output. Inspect the actual bytes with `ffprobe`, including format, selected audio stream, codec, channels, sample rate, duration, and file size.
2. Reject missing or empty files, absent audio streams, invalid numerical metadata, and unsupported profiles. An untrusted filename extension does not establish format.
3. Preserve compatible valid audio without unnecessary lossy encoding. When metadata repair is needed, remux to a seekable local temporary file and explicitly finalize container metadata. For MP3, enable the Xing header; for M4A, use the appropriate MP4 finalization/fast-start settings. These are different container operations.
4. Validate the completed output through a full decode and compare measured timeline/sample duration with reported duration using documented codec-delay and rounding tolerances. If remuxing leaves invalid frames or inconsistent timing, reject or re-encode under an explicit repair policy. Record source diagnostics; a decoder skipping corrupt input does not establish that the original content was complete.
5. Enforce the actual final byte limit. When necessary, use bounded re-encoding or ordered segments with a configured minimum quality. Never assume a bitrate calculation guarantees the size limit, or reduce speech quality without a floor.
6. Publish by atomic rename only after validation. Keep the raw and finalized artifacts separately addressable until the configured retention policy permits cleanup.
Do not concatenate complete MP3 files as an unvalidated final output. A local synthetic example containing 3 seconds of sine audio plus 17 seconds of noise produced approximately 49.48 seconds of probed duration after binary concatenation, although decoding yielded approximately 20.07 seconds. Remuxing repaired the duration but left a decode error; re-encoding yielded a clean decoded output. This is a regression-fixture mechanism, not a reproduction of the user's incident.
## 3. Artifact manifest
Use a versioned, machine-readable manifest. Store at least:
- `schema_version`, `artifact_id`, `content_sha256`, `byte_length`, and relative storage reference.
- Input document version, spoken-text hash where applicable, parent artifacts, and derivation key.
- Producer/version, requested profile, effective encoding settings, format, codec, MIME, channels, and sample rate.
- Measured `duration_ms`, validation result, validation-tool versions, and bounded diagnostic references.
- Segment ordinal, total segment count, and validated timeline offsets when segmented.
Use content hashes for byte identity and explicit relationships for derivation identity. Store Telegram delivery receipts separately: a single artifact can be sent many times. Do not put local absolute paths, credentials, signed download URLs, or volatile delivery metadata into portable archive manifests.
## 4. Telegram presentation and delivery
Expose two explicit presentation profiles: `audio_track` and `voice_note`. Speech defaults may select `voice_note`; users can request a titled audio track. Current Bot API documentation accepts MP3/M4A for `sendAudio`, and OGG/Opus, MP3, or M4A for `sendVoice`. A validated OGG/Opus profile is a reasonable speech default, not the API's only accepted voice format.
Always provide the validated duration rounded to documented integer-second semantics, the appropriate MIME, and escaped captions. Do not falsify duration to unlock a client feature. Telegram Desktop v7.3.3 permits variable speed for voice/video messages or ordinary audio lasting at least 20 minutes. Thus even a completely valid short `audio_track` need not display the same controls as a voice note. Verify the intended behavior on supported clients and record their versions; do not promise identical UI across all Telegram applications.
Write a delivery outbox entry before any network send. Persist the returned message identifier, media type, duration, `file_id`, and `file_unique_id`. Validate the response against the requested presentation and expected duration; `ok=true` alone does not complete product acceptance. Reusable `file_id` values are scoped to the bot identity and media representation. `file_unique_id` identifies media across time/bots but cannot itself be used to resend or download. Keep an upload fallback when a cached identifier is rejected.
Use states such as `pending`, `sending`, `confirmed`, `failed_retryable`, `failed_terminal`, and `delivery_unknown`. Honor explicit rate-limit retry guidance. A timeout after request transmission can mean Telegram accepted the message but the response was lost. Record that ambiguity; do not advertise exactly-once external sending. The MVP should retain unknown attempts and offer an explicit retry that explains duplicate risk. Before attempting a send, persist its attempt identity; a crash while sending must recover conservatively.
Retain artifacts while delivery is pending, retryable, or unknown. A retry reuses validated artifacts and must not rerun translation or speech synthesis. Garbage collection checks references and retention policy. Interrupted jobs resume from recorded stages, while malformed media never becomes a confirmed reusable artifact.
